On the player's device: browser and phone

On-device: the browser keeps Moonshine base; the phone should switch to it

Nothing new beats Moonshine base in the browser on both sets. Whistle is the light option (18 MB, a quarter of the RAM, about as fast) but 3 to 8 points less accurate. On the phone, the app's streaming zipformer is the weakest engine measured; the same sherpa-onnx runtime runs Moonshine base, which is 10 to 19 points better.

Best

  • Browser: Moonshine base stays the default. Best accuracy of anything that runs in a normal (not cross-origin-isolated) page on one WASM thread: 67.2% / 75.0%. Whisper tiny.en scores higher but takes about 4 s per transmission in WASM.
  • Phone: Moonshine base through sherpa-onnx (67.8% / 76.9%, sent wrong 5.9% / 1.9%), a model swap inside the runtime the app already has (its engine already supports the 'moonshine' kind). Shipped

  • public/voice/stt-worker.js: a Whistle engine (?model=whistle): the Cactus engine's WASM build and the .cact weights from pinned Hugging Face revisions, cached with the Cache API, keyword-biased with the airline names on frequency and the ATC command words; transformers.js is now imported only for the engines that use it; a failed model load is retried on the next push-to-talk.
  • src/lib/voice/recognizer.ts: the game page's ?stt-model=whistle (or tiny, whisper-tiny.en) picks the on-device model; the default is unchanged (Moonshine base), so the settings label is unchanged.
  • mobile/STT_MODEL_NOTE.md: the exact manifest change for the phone (not built).

What failed or is blocked

  • Moonshine v2 in the browser: transformers.js (4.3.2, 4.4.0-next) has no moonshine_streaming support, and the official @moonshine-ai/moonshine-wasm 0.1.6 ships only a SIMD + pthreads build, which needs COOP/COEP headers the game does not send (a single-thread build has to be compiled from source with emsdk 4.0.8 and ONNX Runtime). Not worth it: v2 small is +3.7 points on US/UK and -0.6 on the Indian proxy against Moonshine base, at 142 MB.
  • WebGPU: this server has no GPU, so headless Chromium has no adapter; every browser number is WASM (one thread, as players without cross-origin isolation get). On a player's GPU Moonshine base would be faster; Whistle has no WebGPU path.
  • Whistle's native x86 engine has a cliff above 5 s of audio (0.2 s → 1.5 s per clip with 2 threads, worse under load); the WASM build scales smoothly (0.73 s under 4 s, 1.9 s over 6 s).
  • Phonon-2.5 English as a 'tiny' phone model: the 157.6 MB file is an MLX (Apple silicon) container; the Android LiteRT CPU build is 0.94 GB and its card reports 6.1 GB peak RAM on a Galaxy S26 CPU run.
  • No real recordings yet: ml/data/gold/live/ is empty, so every number is synthetic speech (Kokoro). The Indian-accent set is Kokoro's Hindi voices reading English, a proxy, not the owner.

Notes

  • Contextual biasing paid off for Whistle only with the command words: names alone 61.6% / 61.9% (one decode), names + ATC words 64.4% / 66.9%; WER 36.7 → 32.7% (US/UK).
  • Where Whistle loses (US/UK, against Moonshine base): late start 56% vs 64% and clean 72.5% vs 77.5%; it ties on laptop (75%) and radio (54% vs 52.5%). On the Indian-accent proxy it is 8 points behind (66.9% vs 75.0%), the gap that matters most for the owner.
  • Sent wrong (a wrong command the game would send) is 2-7% for every engine: the verifier holds back most misrecognitions, so the differences are in how often the player has to repeat.

How it was measured

  • Clips: ml/stt/bench2/clips (160 situations x clean/laptop/radio/late, US/UK Kokoro voices), even ids: 320; ml/stt/bench2/clips_in (Kokoro Hindi voices, clean/laptop), even ids: 160.
  • Score: ml/stt/bench2/score.ts with S1_MODEL=2m-grpo-v1; 'exact' = the game's n-best + repair + S1 chain ends on the gold command; baselines were rescored with today's scorer (the verifier lowered every engine's sent-wrong since round 2).
  • Browser: ml/stt/bench2/edge_browser.cjs, headless Chromium (playwright), the game's worker, 40 clips (mean 5.0 s), WASM; RAM = PSS of all Chromium processes above a blank page (peak); download = bytes fetched. The machine was shared (load average 12-20), so latencies are pessimistic.
  • Phone: mobile/tool/stt_bench.dart (the app's SttEngine and hotword builder, sherpa-onnx on Linux x86, 2 threads).

On the game's server

Server: Parakeet Ultra first, Whisper only when needed (shipped)

Small CPU recognisers that could run beside Whisper base.en in the game's Next.js server, on this VPS's CPU (8-core EPYC, 3 threads, one command at a time). None beats Whisper on its own. As a fast first pass, with Whisper asked only when the game cannot understand the guesses, Parakeet Ultra int8 with the callsigns on frequency as hotwords lifts the Indian-accent proxy from 78.8% to 85.6% exact (p=0.001), ties on US/UK, and answers most commands in about 0.4 s. It now runs in the game.

Best

  • Cascade: Parakeet Ultra int8 (sherpa-onnx, callsign hotwords), then Whisper base.en only when not understood. Ultra was right on 11 Indian-proxy clips where Whisper was wrong, and never the other way round. It runs in Node in-process through sherpa-onnx-node, with output identical to Python on 40 of 40 clips.
  • Granite TurboCTC as the first pass is as good (80.0% / 84.4%) but needs an ONNX port and a front end in JS. Phonon-2.5-English is the fastest good model (0.15 s) but runs only from Python, so it needs a sidecar service.
  • On US/UK the cascade raises commands sent wrong without a check from 6.3% to 7.5%; on the Indian proxy it lowers them from 7.5% to 3.7%.

Shipped

  • src/app/api/voice/stt: a parakeet engine (sherpa-onnx-node 2.0.1, in the Next.js process, loaded on first use, the same 2-3 threads and the same guards as Whisper: one inference at a time, queue, timeout, per-IP rate limit). ?engine=parakeet|whisper or X-STT-Engine picks one. Without either, the server's first pass is Parakeet; OPENATC_STT_FIRST=whisper restores Whisper alone. Hotwords are the telephony words of the callsigns on frequency, per request. The model files are copied once to ~/.cache/openatc-stt/parakeet-ultra-int8 (ml/stt/RESULTS2.md); without them, Whisper answers.
  • src/lib/voice/asr-server.ts cascadeStt: the Server recogniser and the Browser engine's second opinion ask the first pass. When the game cannot understand its guesses, the same audio goes to Whisper and both lists are read together (the benchmark's rule). Settings now says "Server (Parakeet + Whisper, tuned for ATC)". The voice demo page uses the same cascade.
  • Checked in the standalone build (next build, then .next/standalone copied to an empty directory and run on a spare port). Parakeet's transcripts match the benchmark on 40 of 40 clips. On 40 US/UK clips over HTTP the cascade answered in 0.88 s p50 / 2.5 s p95, against 1.32 s / 3.4 s for Whisper alone (Indian proxy: 0.63 s / 2.8 s against 1.36 s / 1.9 s). That pass read the guesses with the rules only, so Whisper was asked more often than in the game. With both models loaded the server uses 2.1-2.3 GB RSS (Whisper alone ~1.2 GB).
  • Licence: Parakeet Ultra weights CC-BY-4.0 (Moondream's post-training of NVIDIA parakeet-tdt-0.6b-v3; ONNX export by the k2-fsa sherpa-onnx project); sherpa-onnx and sherpa-onnx-node Apache-2.0.

What failed or is blocked

  • No real recordings from the owner yet (ml/data/gold/live/ was empty). Every number is synthetic speech (Kokoro), and the Indian set is a proxy (Kokoro's Hindi voices reading English).
  • Phonon-2.5-English needs a Python sidecar (a new service: not done). Granite needs an ONNX port (not tried). Parakeet Redux through moondream Photon uses proprietary kernels and reports telemetry; the open sherpa-onnx build of the same weights scores better.
  • Canary-180M-Flash loops in its decoder (46 s p95).

Notes

  • Cascade rows: the first engine's guesses go through the game chain; only when nothing is understood is Whisper (2-best, prompt) run and both lists mixed. Their latency is an estimate from the quiet pass: first-pass time, plus Whisper's time for the share that asks for it.
  • Nemotron 3.5 Transcribe 30B (on an L4 GPU) and Google Web Speech are references, not server candidates.
  • Details, per-condition numbers and the paired tests: ml/stt/models/SERVER.md.

How it was measured

  • US/UK: ml/stt/bench2/clips, even ids (--every 2): 80 situations x clean/laptop/radio/late = 320 clips, Kokoro US/UK voices.
  • Indian-accent proxy: ml/stt/bench2/clips_in, even ids: 80 situations x clean/laptop = 160 clips, Kokoro Hindi voices reading English (proxy).
  • Chain: nbest+S1: the game chain (repair + n-best + S1 2m-grpo-v1 behind the rules); exact = final command parses to the gold AST; sent_wrong = sent without a check and wrong; callsign = right aircraft.
  • Latency: a separate quiet pass over 40 US/UK clips (mean 5.0 s of audio), one engine at a time, 3 threads.
