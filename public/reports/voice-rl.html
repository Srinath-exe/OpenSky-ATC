Does RL with the game engine as the reward improve the 2 M voice model?

GRPO written from scratch on the S1 model, three reward designs scored by the engine's own parser, and a control that spends the same CPU on plain supervised fine-tuning of the same hard prompts.

start: s1-2m-11ap-swap (2.03 M params)CPU only, 1 thread per runcode: ml/rl/numbers: ml/rl/RESULTS.md
REAL STT · EXACT79.6 → 83.8start → GRPO exact · 1,000 Whisper / Moonshine transcripts
SFT CONTROL · REAL STT82.0same CPU, same hard prompts, with labels
SYDNEY (UNSEEN) · EXACT86.8 → 86.2–87.1flat for every variant (within noise)
VAL · EXACT94.2 → 95.5known airports · GRPO exact

RL helped where the hard prompts were: on 1,000 real recogniser transcripts GRPO lifted exact match from 79.6% to 83.8% (53 rows fixed, 11 broken, p < 0.001), mostly by picking the right aircraft. The SFT control, with the same CPU and the same prompts plus labels, reached 82.0%: GRPO-exact beats it on the same rows (33 vs 15, p = 0.013, one seed each). The label-free verifier reward did about as well as the labelled ones (83.4%). Sydney, the unseen airport, did not move for any method (86.2–87.1 vs 86.8): its errors are fix names and airlines the model has never seen, and RL can only reinforce answers it already samples. Not exported: the Sydney criterion was not met.

The loop

Policythe model being trained, seen as a probability distribution over command lines for a given state and transcript.
Groupk = 8 lines sampled for the same prompt. GRPO compares them with each other instead of training a value network.
Advantagehow much better a sample scored than its own group's mean, divided by the group's spread. Positive: make it more likely.
Clipped ratioρ = π_new / π_old per token, kept inside 0.8–1.2 (PPO) so one batch cannot move the policy far.
KL penaltya cost (β = 0.04) on drifting from the frozen start model, so the policy keeps what pre-training taught it.
Reward hackingthe policy finds outputs that score well under the reward but are wrong; a leaky reward gets exploited, not obeyed.
SFT controlthe same hard prompts and CPU spent on ordinary supervised training with the labels. It answers "was it RL, or just more training on hard cases?"
Callsign trieon while sampling and in every log-prob: the deployed decoder always masks unknown aircraft, so that is the policy we train.

Three rewards, all computed by the engine

a · exact1 if the sampled line equals the label, else 0. Clean but sparse: a group that is all right or all wrong teaches nothing.
b · shapedparsed AST vs the label's AST: 0.1 parses + 0.4 right aircraft + 0.2 right command kind + 0.3 right values (share of matching fields).
c · verifier (no label)0 unless it parses (unknown aircraft never parse) · +0.4 callsign heard in the transcript · +0.4 F1 between the engine's own spoken rendering of the command and the transcript (numbers double). SAY AGAIN = 0.7 when no aircraft was heard.

Checked against labels (never trained on): the verifier scores the gold line above another real command for the same state 96.8% of the time (n=3,000); on the start model's own predictions it separates right from wrong with AUC 0.91 (val) / 0.89 (Sydney) / 0.91 (real STT). Its blind spots: an unseen fix name is one token of the F1, so 'DIRECT HNNO' for 'direct ssyno' still scores 0.8 (47 of 132 wrong Sydney predictions score ≥ 0.8), and climb/descend are ignored, so 'EXPEDITE CLIMB' for 'expedite descend' scores 1.0.

Reward hacking watch

A leaky reward shows up as samples that are wrong but still score high. The shaped reward pays 0.6 for the right instruction to the wrong aircraft and 0.875 for a taxi to the wrong place; the verifier pays 0.98 for a doubled taxiway and 0.87 for a fix nobody said. Those holes were there from step one, but the policy did not grow into them in 20 CPU-minutes: the wrong-but-high share stayed flat (below), completion length stayed at ~10.4 tokens, and the SAY AGAIN rate fell rather than rose, so no collapse to short or safe commands. With β = 0.04 the KL leash reached only ~0.1 nats per token; longer or less-leashed runs would need the holes closed first.

One GRPO step = 16 prompts × 8 samples ≈ 4.2 CPU-seconds on one shared core (the host had a load average of 10–25 from other jobs); the engine's share was 1.7–1.9 CPU-s per run, about 0.15%: parsing is free next to the model. CPU is the bottleneck. On an L4 (~$1/h) the 16 × 8 rollouts would decode as one batch of 128 and the update is a few small matmuls, so a step should take ~0.1 s: the 20-minute run in ~30 s, a full epoch of the 10.6k pool in about a minute, for cents. That would also make k = 16–32, several seeds and the 11 M model affordable.

Next steps

  • Decision for the lead: GRPO-exact is +4.2 on real STT and +1.3 on val, flat on Sydney. Its int8 export matches fp32 exactly (96.3% vs 96.3%, n=300, files in ml/rl/runs/export-check-grpo-exact/). To publish: python3 ml/edge/export_web.py --run ml/rl/runs/grpo-exact --name s1/2m-grpo-v1 --int8 --check 300 --data ml/data/out4/ds/val.jsonl. The policy is sharper (entropy 0.13 → 0.08), so re-check the confidence gate's calibration before switching.
  • Sydney needs its own hard prompts: rename fixes and airlines consistently in state, transcript and label (as the airline swap does) so unseen names appear in training; then RL has correct copies to reinforce.
  • Close the verifier holes before training on unlabelled speech: render with the aircraft's altitude from the state (climb vs descend), match fix names by spelling, weigh tokens the speaker never said more heavily.
  • Seeds: 2–3 seeds of GRPO-exact and SFT to firm up 'RL beat SFT' (p = 0.013 is one seed each); then the usual recipe, SFT followed by GRPO.
  • Move the loop to a GPU with batched rollouts (see above) and run a full epoch with k = 16.
